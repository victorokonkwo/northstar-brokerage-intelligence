# 011. Dashboards in Looker Studio, reading serving views of the published snapshots

| | |
|---|---|
| Status | Accepted |
| Date | 2026-11-20 |
| Deciders | Project owner |

## Context

The requirements call for four dashboards (FR-DASH-01): Brokerage Operations, Market Risk, Treasury, and Executive Finance. They were planned in Streamlit. On 2026-11-20 the owner decided on **Looker Studio**, replacing Streamlit, for all four, with Looker Studio reading Redshift's gold layer (roadmap, Phase 4 decisions). Phase 4 delivers the first one, the operations dashboard (FR-M2-09, KPI-02 to KPI-06). The other three follow with their modules.

The rules the dashboards must keep:

| Rule | Source |
|---|---|
| Dashboards read only published results and contain no business calculations | W5 |
| The operations dashboard's figures equal the mart query results | FR-M2-09 |
| Each page shows its data's snapshot version and as-of time | FR-DASH-01 |

Facts about Looker Studio's Amazon Redshift connector ([sources.md](../sources.md), 2026-11-20):
- **Authentication:** a user name and password only, with a host name or JDBC URL. No IAM.
- **TLS:** optional ("Enable SSL").
- **Source addresses:** `142.251.74.0/23`, already allowed on port 5439 by the data stack.
- **Data sources:** a table or a single custom query.
- **Limits:** 150,000 rows per query, and queries may time out after three to five minutes.

## Options considered

1. **Streamlit**, as first planned. Dashboards would be code in the repository, but they need a host to run on.
2. **Looker Studio on the published copies directly.** The report would have to pick each date's current version itself. That's version logic, which is a calculation, in the dashboard.
3. **Looker Studio on dbt serving views.** One view per published mart shows each date's currently PUBLISHED version only, with its version number and publication time. Looker Studio displays those rows.

## Decision

Option 3 (owner decisions 2026-11-20).

- **Serving views** (`warehouse/dbt/models/serving/`, schema `<dbt schema>_serving`, tag `serving`):
  - one per controls mart: `serving_match_rates`, `serving_exception_monitoring`, `serving_settlement_fails`, `serving_cash_breaks`
  - each joins the published copy with `snapshot_timeline` on status `PUBLISHED`, and adds `snapshot_version` and `published_at`
  - same grain as the mart, with contracts enforced
  - they exist only after publication, so a default selector (`selectors.yml`) leaves them out of every build not run with `--select tag:serving`. They are built after the controls publication: `make serving`, the DAG's `serving` task, and the cloud run's `serving` step
- **The report calculates nothing.** Every chart shows rows at the view's grain, or one value per date (`docs/dashboards/operations.md`). Totals the marts don't hold aren't shown.
- **A read-only database user, `looker`.** It has USAGE on the serving schema and SELECT on its views, and nothing else.
  - **Who creates it:** the admin, with `northstar redshift-bootstrap --looker-user`.
  - **Its password:** generated by `make env` into the git-ignored `.env` and entered in Looker Studio. It's never stored in AWS or Git.
  - **Its access on rebuild:** dbt replaces views on each build, so its SELECT comes from default privileges for the pipeline users that build them.
- **The connection** uses TLS ("Enable SSL"). Redshift requires it (`require_ssl = true`).
- **Proof of FR-M2-09:**
  - `make dashboard-check` checks that every view shows only the currently published version of each date, equal row for row to that snapshot and to the dbt mart. It runs in CI.
  - After the report is built, three of its figures are compared with the serving views, and the result is recorded.
- **The owner builds the report** in Looker Studio from the spec (owner decision, Phase 4 plan).

## Consequences

- **The report isn't code.** Changes to it aren't reviewed in Git. The spec and the dashboard check are the controls, and a change to a view's columns needs the report updated by hand.
- **A password exists.** It is the project's only database password outside Secrets Manager. It sits in the operator's `.env`, with access to the serving views only. Rotating it means changing `.env`, rerunning the bootstrap, and updating Looker Studio.
- **Freshness:** the serving views are views, so the report sees a publication as soon as it is written. Looker Studio's own caching isn't documented on the connector page.
- **The other three dashboards** reuse the pattern: a serving view per published mart, and a check.

## Revisit when

- **A dashboard needs interaction** Looker Studio can't express without calculating.
- **Data outgrows the connector's limits** (150,000 rows per query, a few minutes per query).
- **IAM or short-lived credentials** become available for the connector.
